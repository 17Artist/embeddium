# Translucent sorting performance

Gene Fork 0.3.31-gene.2 changes large transparent-mesh sorting only. Meshes below
4,096 quads keep merge sorting; larger meshes use the existing Fastutil radix sorter.
Equal-distance faces keep their original index order. NaN distances take the original
comparison path. Distance calculations, visibility, scheduling and OpenGL requirements
are unchanged. No additional dependency or user setting is required.

## Measurement

Minecraft 1.20.1, Forge 47.3.22, Java 17.0.7, RTX 3060 Ti. Aperture 3.3.0,
GeneVisage 1.0.25-41013 and the 3.3.0 bridge were installed in both versions.
Four serial clients ran in old/new/new/old order. Each case used actual glass meshes
generated by the game, 512 warmup jobs and 768 measured jobs. Timing includes the
complete `ChunkBuilderSortTask`, index-buffer allocation/generation and disposal.
Hash comparison and framebuffer capture were outside the measured region.

| Mesh | Quads | gene.1 CPU / ms | gene.2 CPU / ms | Reduction |
| --- | ---: | ---: | ---: | ---: |
| layered-glass | 2,104 | 0.100 | 0.103 | -3.2% |
| dense-glass-columns | 8,448 | 0.489 | 0.324 | 33.7% |
| dense-glass-cubes | 12,288 | 0.648 | 0.501 | 22.6% |

Values are the mean of two per-run medians. This is a targeted CPU workload result,
not an FPS uplift. It benefits large, dynamically sorted transparent meshes; ordinary
small windows and GPU-bound scenes should not be expected to become noticeably faster.

## Correctness and scope

- 864 exact-order checks cover threshold edges, ties, signed zero, infinities and NaNs.
- Game-generated vertices and sorted index buffers matched the old version for 64
  camera positions in each of three fixtures.
- The earlier 1,000-case terrain-list regression check remains enabled.
- An experimental lazy biome-preparation change was discarded: complete mesh-build
  measurements improved by only about 1-3%, below the value sought for this pass.
- Worker scheduling, mesh merging, visibility rules and buffer submission were reviewed
  without changes. Further work would require a demonstrated bottleneck in a representative
  workload rather than assumptions about general FPS.
